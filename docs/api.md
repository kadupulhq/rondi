# Internal API and durability

The API is versioned under `/v1` and uses HTTP/1.1 with JSON over a Unix domain socket. It binds no TCP listener. The socket is created with mode `0600`; filesystem ownership is the local access control. Remote listening, authentication, and TLS are not implemented; enabling a network listener without authenticated transport is unsupported.

## Endpoints

| Method and path | Request | Result |
| --- | --- | --- |
| `GET /v1/health` | none | `{"status":"ok","api_version":1}` |
| `POST /v1/databases` | `{"name":"cpu","config":{"step":10,"heartbeat":25,"rows":6,"start":1700000000}}` | `201` after the `.rondi` file is synced |
| `POST /v1/databases/{name}/updates` | `{"id":"collector-1-1700000010","timestamp":1700000010,"value":2.5}` | `200 {"status":"durable"}` after journal and storage sync |
| `GET /v1/databases/{name}/points` | none | retained closed AVERAGE points and step |

`rows` must be between 1 and the server's `--max-rows` (default 100000); larger values are rejected with `400`. Use JSON `null` for an explicitly unknown sample. Repeated or older update timestamps are rejected. Request IDs are recorded in the journal for replay and retry deduplication; clients should make retries with the same logical ID and timestamp. A retry is deduplicated for at least `--idempotency-window` seconds (default 86400); after that the journal may have been compacted and the retry is treated as a new update (see [architecture.md](architecture.md#store-limits-and-journal-compaction)).

The bounded server queue defaults to 256 pending writes and is configurable at startup. A full queue responds `429` without accepting the update. Accepted updates are journaled before the acknowledgement; a crash after journal sync and before database checkpoint is recovered at restart. A partial last journal line left by a crash mid-append was never acknowledged; it is truncated before replay or the next append. Success means journal and database files passed `sync_all` and the containing directory was synced for the database rename. This guarantee depends on filesystem and hardware honoring sync requests. If checkpointing fails after the journal was synced, the request may still be replayed; a `503` therefore has an uncertain outcome. Retry the exact request ID and payload to resolve it idempotently.

On Unix, `SIGINT` and `SIGTERM` stop accepting new connections, drain active requests and accepted writes, and remove the socket path on clean shutdown. The drain is bounded to 30 seconds; after that the server aborts remaining connections and logs `shutdown_drain_timeout`.

## `rrdcached` compatibility alias

The `rrdcached` invocation is a separate ASCII-protocol adapter, not this JSON API. Its implemented subset listens on a Unix socket. Use `-p <file>` to write and clean up a PID file; a live PID owner is rejected and stale PID files are replaced. Rondi does not use upstream's default system PID path. `-o <file>` appends structured operational logs there; its format and level controls differ from upstream logging. `FETCHBIN` emits the upstream status and metadata lines, then a per-data-source binary block containing native-endian IEEE-754 doubles; the response is byte-differentially tested on disposable files. `DUMP <file>` streams default-DTD XML without a line-count prefix and closes the connection to mark the end, matching RRDtool 1.11.0; its handler ignores trailing header options. `TUNE` supports the basic heartbeat, min/max, DS type, and DS rename operations using the upstream argc/argv[0] wire format. An `UPDATE` success response has upstream framing (`0 errors, enqueued N value(s).`); it means every submitted sample has been appended to `.rrdcached.journal` in the configured `-j` directory (or the storage root when omitted) and `sync_data` completed, though the `.rrd` file may not have changed yet. `CREATE` refuses to replace the journal, `.rondi.lock`, or `rondi.journal`. Pending entries replay on restart and are applied on `FETCH`, `FLUSH`, periodic `-w` timeout (default 300 seconds; integer and suffixed durations such as `5m` are accepted, while zero is rejected like upstream), or graceful shutdown. `PENDING` reports accepted samples not yet flushed. `SUSPEND` and `SUSPENDALL` pause flushes for known cache entries; `RESUME` and `RESUMEALL` resume them, and suspend state resets after restart. The pending queue is limited to an estimated 64 MiB by default; a full queue rejects new updates before journaling them. Startup refuses a recovered queue larger than that limit so accepted writes are not silently discarded. `FORGET` durably removes pending entries without changing the RRD file. Replaying a record whose file update completed before a crash is idempotently skipped based on the RRD last-update timestamp. Replay drops a partial final record left by an interrupted append and skips malformed lines with a warning, as upstream does, instead of refusing to start. Each `-f` flush interval rewrites the journal to hold only pending updates (synced, then renamed into place), and `STATS` `JournalRotate` counts these rewrites. This behavior and the tested command subset are partial compatibility only; it does not establish upstream rrdcached parity.

## Errors

Errors use JSON objects with stable `error.code` and `error.message` fields. HTTP statuses are `400` for invalid operations, `404` for unknown routes/databases, `409` for conflicts or duplicate/out-of-order timestamps, `413` for requests over the 1 MiB limit, `429` for queue pressure, `500` for corrupt or unsupported storage, and `503` for storage/worker failures. Health currently reports process/API liveness only, not storage latency or disk capacity.
